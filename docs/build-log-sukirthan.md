## 1. What I built

A FastAPI backend that scores a spoken attempt at a target speech sound and
returns a per-phoneme breakdown in a frozen JSON shape. It ships in two modes
behind one environment switch: a permanent **stub** engine that returns
realistic, contract-shaped fake scores with real clinical feedback (default,
zero heavy dependencies, the demo safety net), and a **real** wav2vec2 phoneme
CTC engine (`REAL_ENGINE=1`) that recognises the actual phonemes, converts the
model's IPA output to ARPAbet, aligns it against the expected sequence, and
scores each phoneme. Any failure or a breach of the 4-second latency budget in
the real engine falls back to the stub automatically, so a user action can
never produce a 500 and the demo can never hang.

## 3. How scoring actually works, explained (for a reader who has never heard of CTC)

1. **Audio arrives** as a webm/opus blob (from the browser's MediaRecorder) or a
   WAV upload.
2. **Resample to 16 kHz mono.** The model was trained on 16 kHz audio; anything
   else confuses it. `librosa.load(..., sr=16000, mono=True)` handles decoding
   and resampling in one step.
3. **The model emits per-frame phoneme probabilities.** wav2vec2 chops the audio
   into ~20 ms frames and, for each frame, outputs a probability distribution
   over its phoneme vocabulary plus a special "blank" token. So a 1-second clip
   becomes ~50 rows, each row a vote for "which phoneme is happening right now,
   or nothing".
4. **Greedy CTC decode to a phoneme sequence.** CTC (Connectionist Temporal
   Classification) is the trick that lets a model label audio without knowing in
   advance where each sound starts. We take the most likely token per frame,
   then collapse runs of the same token and drop the blanks — so
   `S S S _ _ AH AH _ N N N` becomes `S AH N`. That collapse is the whole point
   of CTC: the model never had to be told the boundaries.
5. **IPA → ARPAbet.** This particular model speaks IPA (`s ʌ n`). The contract
   speaks ARPAbet (`S AH N`). `ipa_arpabet.py` converts at the boundary using a
   longest-match-first table, so the frontend never sees IPA.
6. **Align against the expected sequence.** We know what they were *asked* to say
   (`expected`). We Levenshtein-align what we *heard* against it, producing
   exactly one output entry per expected phoneme — with `None` where a phoneme
   was deleted (not produced at all).
7. **Per-phoneme scores.** A correctly-produced phoneme scores 60–100 scaled by
   the model's confidence; a substituted phoneme scores 35; a deleted phoneme
   scores 15. Each gets a status: correct (≥75) / close (50–74) / incorrect (<50).
8. **Feedback selection.** We look at the target sound specifically. If it was
   substituted, we name the substitution ("it came out as SH — pull your tongue
   tip forward").

**Why per-phoneme scoring matters:** a single 62% for the whole word tells the
learner nothing actionable. Scoring each phoneme and aligning it to the expected
sequence is exactly what lets the product say *"you produced SH instead of S"* —
which is the clinical value. One number is a grade; a per-phoneme breakdown is a
lesson.

## 4. The model

- **Which:** `facebook/wav2vec2-lv-60-espeak-cv-ft`.
- **Why that one:** it is a *phoneme* recogniser (most ASR models give you words
  only). It works at the isolated-sound level — the very first step of the demo —
  which a word-level Whisper transcript cannot do. The alternative (Whisper) was
  kept only as a conceptual net; Engine A is the target because Engine B cannot
  score a single phoneme.
- **What it emits natively:** IPA phoneme tokens (espeak flavour), e.g. `s`, `ʌ`,
  `ʃ`, `θ`, `ɹ`.

**Raw vocabulary — MEASURED.** The model was downloaded and probed. Its vocab
has **392 tokens** (`pad_id=0`). It is a *multilingual* espeak phoneme set — it
carries far more than English: tones (`i5`, `a2`, `onɡ5`), retroflexes
(`ʈ ɖ ʂ ʐ ɳ ɽ`), uvulars (`ʁ χ ʕ`), front-rounded vowels (`y ø œ`), nasalized
vowels (`ɐ̃ ã õ ẽ`), and espeak markers (`S N X ??`). The English-relevant tokens
it emits are the ordinary IPA ones: `s z ʃ tʃ dʒ θ ð ɹ l k ɡ f ɐ ə ɪ ᵻ ɫ …`.

**IPA→ARPAbet coverage — CHECKED against the real vocab.** Of the 392 tokens,
314 map through the table and **74 map to nothing**. I did not silently drop
them — I inspected all 74. Almost all are the non-English phonemes above, which
will never appear in an English speaker's production of the target words; if one
ever does, it is skipped, which is correct. **Three were English-relevant and
the starter table missed them**, so I added them (this is the only change I made
to the provided `ipa_arpabet.py`):
- `ɐ` (near-open central) → **AH**
- `ᵻ` (reduced barred-i) → **IH**
- `ɫ` (dark/velarized L) → **L**  — matters: "penci**l**" ends in a dark L
Syllabic `l̩`/`n̩`/`r̩` already resolve (base consonant maps, combining mark is
skipped). Glottal stop `ʔ` and palatal `ç` are deliberately left unmapped and
documented in the file — they are ambiguous in English and mapping them risks
phantom phonemes.

**Raw single-clip output — MEASURED.** On a synthetic 0.6 s tone the model emits
all `<pad>` (blank) frames → CTC-collapsed to `[]` → ARPAbet `[]`. That is the
correct behaviour for non-speech: an empty `heard`. (Real phoneme output requires
real speech, which I cannot record here — that is what calibration in §10 is for.)

**Important dependency finding (see §13):** this model's HF tokenizer
(`Wav2Vec2PhonemeCTCTokenizer`) requires the **`phonemizer`** pip package AND the
**`espeak-ng` system binary**, neither of which the spec's Day-2 dependency list
includes. Its decode direction does not need espeak, so `engine.py` was hardened
to load the feature-extractor + `vocab.json` directly and skip the tokenizer —
the real engine now runs even on a machine without espeak-ng.

## 5. The stub and the fallback

**What the stub does:** deterministic-ish fake scoring seeded by audio length
and target text, so the same input gives a stable, plausible-looking result. The
target sound is made to vary most, so demos are readable. It emits the exact
frozen response shape, including real feedback tips from `feedback.py`.

**Why it is permanent:** it is the demo insurance. It has zero heavy
dependencies, always responds in milliseconds, and never fails. If the model
won't load, is too slow, or throws on a weird input, the stub answers instead —
honestly reporting `"engine": "stub"`.

**The exact environment flag:** `REAL_ENGINE=1` selects the real engine at
startup. Unset (or `0`) = stub. On demo day you choose which `uvicorn` command
to run.

| `duration_ms` | int | stub: summed durations; engine: real clip length |
| `engine` | stub/whisper/wav2vec2 | set in main.py after scoring |

**How `len(phonemes) == len(expected)` is guaranteed on EVERY path:**
- **Stub path:** `stub.score()` builds `phonemes` by iterating `for sym in
  expected:` — exactly one append per expected symbol. Structurally impossible to
  produce a different count.
- **Real path:** `engine.score()` iterates the alignment `pairs`, and `_align`
  returns exactly `len(expected)` pairs (the while-loop runs until `i == 0`,
  emitting one pair per expected symbol, with `None` for deletions). One append
  per pair → one phoneme per expected symbol.
- **Fallback path:** if the real engine raises or is too slow, `main._run_scoring`
  discards its result and calls `stub.score()` with the *same* `expected` — back
  to the stub guarantee.
- **Error paths** (400/422) return before any scoring, so they never emit a
  phonemes array at all.
Every code path that returns a `phonemes` array builds it from `expected`.

## 9. Latency

Stub: sub-millisecond per request (no model). **VERIFIED** via the `[score]`
log line printing ms per request.

**Real engine (CPU, this build VM) — MEASURED.**

- **Cold-start bug found and fixed.** The model is loaded at startup, but the
  first request still paid **librosa/numba JIT + torch graph warmup** — measured
  as a **>30 s first click** (a 30 s client timeout on request #1). Loading the
  model at startup is not enough on its own. I added `_warmup()` to
  `engine.load()`: it runs the full decode+inference path once on 0.3 s of
  silence at startup, JIT-compiling both paths before any user request.
- **After the fix, warm start holds:** on a pre-warmed server, request #1 = 2694 ms
  vs request #6 = 2553 ms — within noise, no cold outlier.
- **4-second rule on a 3-second clip:** mean **2574 ms**, median 2554 ms, max
  2694 ms over 6 requests — **all under 4 s. PASS.**
- **By clip length:** 0.6 s → ~2.2 s, 3.0 s → ~2.6 s, 10 s → ~3.9 s.
- **Caveat (honest):** under CPU contention (a second server + load-test
  processes running) the same 3 s clip spiked to 3–6 s and occasionally over 4 s.
  torch CPU latency is machine- and load-dependent. Benchmark the actual demo
  laptop before presenting; keep other heavy processes off it. The latency
  fallback (marks `engine: stub` when a call exceeds 4 s) is the safety net, and
  it was observed firing on the 10 s clip.

## 12. Honest limitations (put this in the pitch)

This system detects **substitutions** — the learner produced a *different*
phoneme than the target (said SH instead of S). That is exactly what the
recognise-then-align pipeline is good at: a different phoneme shows up as a
different token.

It does **not** reliably detect **distortions** — the *right* phoneme produced
imprecisely (a slushy but recognisably-S "S", a mushy R). To the recogniser that
is still an S, so it scores well even though a clinician would mark it. Distortions
are a large share of real articulation disorders, so this is a real limit, not a
footnote. We say it out loud because naming it — with calibration numbers behind
it — reads as competence; being caught out by it reads as the opposite.
